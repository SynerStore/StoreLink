# StoreLink 产品完成度分析

> 分析日期：2026-08-05 ｜ 分析分支：`feat/worker_threads` ｜ 方法：源码走查 + 多 agent 分系统勘察 + tsc / 测试验证

## 总体判断

**界面层完成度高（约 80%），核心功能链路完成度低（约 50%），存在多处"界面在、后端断"的功能断点。整体处于「可演示的 alpha / 早期 beta」状态，距离可对外发布还有一段硬距离。**

工具本质：Electron + React + TS 的跨平台多存储管理客户端（~2 万行源码），管理本地 + S3/OSS/COS/华为 OBS/SFTP/WebDAV/群晖 Synology。当前 `feat/worker_threads` 分支正在做 worker 线程池任务系统。

**综合结论**：这是一个**「架构和 UI 成型、核心写/传输链路未贯通」的早期 beta**。对个人工具而言已相当能用（浏览、预览、基础上传下载在 S3/OSS 等路径可用）；但要对外发布，仍需补齐 P0 功能断点 + 安全加固 + 完成一次真实打包发版。

## 二、必须知道的三个核心断点

### 1. 跨存储复制/移动 —— UI 完整，实际必失败

- `FileTransferModal`（`src/renderer/components/FileTransferModal/index.tsx`）完整实现了"选择目标存储 + 目录树"的界面，是产品差异化卖点。
- 但断链有三层：
  - worker 的跨存储分支需要 `task.sourceConfig/sourceStoreType`，而调度器 `scheduler.ts:64-73` 从不传这两个字段 → 永远走"同存储"路径；
  - **没有任何一个适配器实现 `getReadStream`/`putWriteStream`**（接口声明于 `store.ts:22-23`，全仓 0 实现）→ 流式管道分支是死代码；
  - fallback 的 `get`/`put` 参数形状也对不上（`get` 需要 `localPath`，`put` 期望 `localPaths+prefix`，见 `oss/api.ts:101`、`oss/api.ts:260`）。
- 结论：**用户能选目标存储，但点确认后任务必然报错**。

### 2. COS（腾讯云）适配器方法名错配 —— 下载/删除/复制全断

- `CosStore`（`src/main/stores/adapters/cos/index.ts`）把方法命名为 `getObject/deleteObject/copyObject`，但渲染端和 worker 统一按接口名 `get/delete/copy` 调用（如 `CosViewer/index.tsx:97`）。
- 结果是 worker 抛 `Method get not found in store`（`storage.worker.ts:169`）→ **COS 的单文件下载、删除、复制任务在运行时全部失败**。`listDir` 还和 `list` 完全一样、不筛目录（`cos/index.ts:110-117`）。

### 3. 更新服务是空壳

- `update.ts` 仓库地址是占位符 `'your-username/your-repo'`（`services/update.ts:31`）；
- `downloadUpdate` 把响应流读出来直接**丢弃不落盘**（`update.ts:271-300`），`installUpdate` 空操作返回 `{ success: true }`（`update.ts:306-326`）。
- 即"检查更新"永远失败、"安装更新"假装成功。

**另外**：`copy` 方法在 SFTP/WebDAV/Synology 也全部缺失，仅 S3/OSS/Local 可用 → 复制/移动操作在这些存储上同样不可用；`OBS` 目录是 0 字节空文件（华为云实际走 S3 适配器，`constants.ts:19-21`）。

## 三、设计文档 vs 实现差距（任务系统）

`docs/design/任务创建和调度的设计.md` 承诺的架构相当完整，但落地打折：

| 设计承诺 | 实现状态 |
|---|---|
| Group/子任务分级（文件夹递归拆分） | ❌ 无目录扫描器，进度按文件数而非字节 |
| 流式管道 + 校验和 | ❌ 无适配器实现流式方法 |
| checkpoint 断点续传 | ❌ 字段存在（DB schema）但无续传逻辑，重启恢复仅 RUNNING→PAUSED |
| 可重试 vs 致命错误分类 | ❌ 所有错误一律重试 3 次（指数退避） |
| 每连接并发限制 | ✅ `maxTasksPerConnection=3` |
| 进度节流 + IPC 批量 | ✅ worker 500ms/1%，main 100ms 批量 |
| 带宽限制/优先级抢占/差异同步 | ❌ 明确列为后续迭代 |

## 四、渲染端 UI 细节问题

1. **音频预览是"可达但必败"的空档**——`getFiletype` 把音频映射到 `'audio'`、`isCanOpenFile` 放行、`openViewer` 会打开，但 `FileViewer/index.tsx` 没有 `audio` 分支，也没有 `AudioViewer` 组件 → 用户点开音频文件一定看到"不支持"。这是和跨存储传输一样的"链路通到一半断掉"。
2. **任务小窗（task-panel）整页硬编码中文**，未走 i18n。
3. **英文 locale 缺 `tasks.detail.*` 的 10 个 key**（zh 有、en 没有），而 `TaskLogTable`/`TaskDetailModal` 正在使用 → 英文用户会看到原始 key 字符串。
4. **`SyntaxHighlightViewer` 把 JSON/CSS/YAML 全按 JS 高亮**（`language={'javascript'}` 硬编码）。
5. **下载按钮和搜索框在全部 7 个 viewer 里都是死控件**——逐一确认：下载按钮 `onClick={() => {}}` 或缺失、搜索框无 `onChange`。这不是个例，是普遍现象。
6. 拖拽移动到文件夹仅 LOCAL/COS/OSS 实现，S3/SFTP/Synology/WebDAV 缺失；LOCAL/Synology/WebDAV 的文件操作还绕过任务系统（直接 `storeRequest`，不进任务面板、无进度）。
7. **launch 启动屏是 `<div>launch</div>` 占位**，但主进程确实有个 `LaunchWindow` 会展示它。
8. 死代码清单：`EmptyState`（构建完整但零引用）、`docx.png` 等图标资产无引用、`FileDeteleWrap` 拼写错误。

## 五、安全（发行前必须处理）

- **高风险**：viewer 窗口 `webSecurity:false + nodeIntegration:true`（`viewer/window.ts:18-24`）+ 全仓无 CSP。`@uiw/react-markdown-preview` 开启 `rehype-raw` 无净化 → 云端一个恶意 `.md` 即可通过 preload 的通用 `dispatch` 调用**所有 IPC**（读/删任意已配置存储、导入连接、读日志）。
- 通用 `dispatch(channel, data)` 无 channel 白名单（`preload.ts:17-40`）；`storeRequest` 任意 method 动态分发、无校验无 try/catch（`stores/index.ts:47`）。
- 正面项：凭据落盘 AES-256-CBC + PBKDF2(150k)、主进程临时解密即清、明文永不发渲染端 —— 这块做得不错。
- 中等项：加密密钥基于 machine-id（同机进程可推导，`secret.ts:22-26`）；密码长度元数据（`xxxLength`）泄漏给渲染端；日志可能含 SDK 报错明文。

## 六、工程化与质量

- ✅ 32 个测试通过（6 文件：utils/cos api/本地 API/性能基准）；文档完备（DEVELOP/OPTIMIZATION/security/design）。
- ❌ 适配器与任务核心**零测试**；`tsc --noEmit` 存在 **66 个严格模式类型错误**（多数是 unused locals，但有几个是真 bug：`registry.ts` 的 dispatch 传参错误、local `fs.copy` 的 `string|undefined`、任务状态表 enum 缺 `SCANNING/RETRYING`、antd v6 API 漂移）；无 CI（`.github` 不存在）、无 eslint（仅 prettier）；无单实例锁、无 crash handler。
- ❌ **`dist/` 里没有任何安装包产物**——打包管线存在（`make.js` 是完整实现）但从未成功跑出 .dmg/.exe。这印证了"可开发运行，未真正发版"。
- `any` 泛滥：main 249 处、renderer 311 处；`IStorageHandler` 17 个方法**全部可选**（`store.ts:5-23`）→ 缺方法只在运行时暴露。
- **worker 线程路径其实是完整接线的**（`storage.worker.ts` 不是死代码）——它被 viewer 和 task 系统真实使用，`build/storage.worker.js` 已产出。真正的断点是适配器侧（`getReadStream` 全缺、COS 方法名错配、跨存储 `sourceConfig` 不传）。
- `react-resizable` 和 `lowdb` 是死依赖（被依赖但零 import），可清理。

## 七、优先级建议

**P0 — 阻断发布的功能**
1. COS 适配器方法名对齐（`getObject→get` 等），或让 dispatcher 兼容两种命名；
2. 跨存储传输真正接线（传 `sourceConfig` + 至少落地 get/put buffer 路径，或实现流式）；
3. 更新服务落地（接真实 GitHub Releases + electron-updater）或从 UI 移除。

**P0 — 安全**
4. viewer 窗口关 `nodeIntegration`/开 `webSecurity` + 全应用 CSP；
5. IPC channel 白名单 + `storeRequest` 方法白名单与入参校验；
6. Markdown 预览净化 HTML。

**P1 — 体验**：文件夹任务拆分子任务 + 字节级进度；checkpoint 续传；音频预览；清掉死按钮/死搜索框（7 个 viewer 全量）；任务小窗国际化 + 补全 en 的 `tasks.detail.*` key。

**P1 — 工程**：tsc 66 错误清零 + 加 CI + 加 eslint；为 COS/任务调度补单测；清理死依赖与死代码（`EmptyState`、`docx.png`、`react-resizable`、`lowdb`）。

**P2**：清理 OBS 空壳；OSS 支持自定义 endpoint（MinIO）；隐私协议合规（当前弹窗有 bug 未修）。

---

## 一句话总结

> StoreLink 是一个**架构和界面都已成型、但核心能力链路有多处断裂**的早期 beta 工具。连接管理、文件浏览、预览这些"读"路径完成度高；而"写/传输"路径——COS 下载删除、跨存储复制移动、更新安装——存在确定的运行时断点。当前最像的状态是**「内部可用的 alpha，面向外部仍需补 P0 功能断点 + 安全加固 + 完成一次真实打包发版」**。
